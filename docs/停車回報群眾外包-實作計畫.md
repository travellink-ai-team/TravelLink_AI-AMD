# 停車回報 → 群眾外包停車點 — 實作計畫

> **任務**：本地端資料沒有停車資訊的地點，徵求使用者到現場自行找位並回報；累積夠多筆就建檔，讓後來的人有停車點可用
> **狀態**：規劃中（2026-08-04 擬定 → 修正收件人前提 → 經兩輪 Codex 審查後大幅修訂）
> **核心結論**：回報的收件人是**未來的使用者與系統**，不是當下的同行者。這決定了整份計畫的優先順序。
> **前置條件**：階段 0 必須先做——目前的回報沒有座標，而沒有座標就沒有任何東西可以聚合。
> **⚠ 這個功能沒有立即受益者**：詳見 1.3 與 6.5。若不做 1b（個人層級立即生效），它在使用者規模夠大之前是空轉的。

## 一、問題定義

### 1.1 現有基礎

| 既有資產 | 位置 | 可重用之處 |
|---|---|---|
| 停車解析四層退回 | `resolveParkingCoord` `:13910` | 社群點接在**第二層**（本地資料），零 API 成本。⚠ 第一層是 `getEmbeddedParkingHint`，會短路，見 1.2 缺口四 |
| 本地停車場資料 | `getLocalParkingList` `:13880` → `app/parking-data.js` | 社群點的落地目標 |
| 停車位置記錄 | `openParkingRecordSheet` `:1257`、`saveParkingRecord` `:1338` | 已有 GPS＋地圖拖曳微調，是座標的來源 |
| **GPS 精度** | `setParkingDraft` `:1186`，欄位 `accuracy` | 品質守門（5.3）；UI 已在 >30m 標紅（`:1201`） |
| **手動修正旗標** | `adjusted`（設定於 `:1189`／保存於 `:1270`、`:1357`） | 使用者拖曳過的點＝高信心 |
| 停車回報表單 | `openParkingReportSheet` `:1378`、`submitParkingReport` `:1398` | 狀況分類的來源（需重整，見 3.2） |
| **後端代理與 Admin SDK** | `server/server.js`（`generation_runs` 為既有先例） | **階段 1 的寫入邊界**，見第四節 |
| 停車場資料管線 | crawler `--crawl-parking` → `parking_lots` → `export:local` | 促進後的社群點走同一條路 |

### 1.2 現況診斷

**缺口一：回報沒有座標。**
`submitParkingReport` `:1398` 存的是 `{ id, stopId, stopName, type, note, at, uid, displayName }`——**沒有 lat/lng**。
而 app 另一邊的「記錄停車位置」有 GPS＋拖曳微調，兩個功能互不相通。

**缺口二：回報現在比想像中公開。**
存在 `micro_trips/{tripId}.tripProgress.parkingReports`（`persistParkingRecords` `:1164`）。
`firestore.rules:343-350` 的讀取條件包含 `resource.data.get('inviteCode','') != ''`——
規則註解自己寫明語意是「**有分享碼的行程，任何登入者可讀**」。
共編行程一律有 `inviteCode`，因此現況的停車回報（含備註、uid）**對任何登入者都可讀**。
跨使用者聚合仍不可能（資料散在各行程文件裡），但「私有」這個描述不成立。

**缺口三：`type` 被壓成布林值。**
`:1427-1428` 把五種狀況壓成 `stage.parkingFound = type === 'found'`，且會在下一次重畫路線時被 `:14476` 覆寫。

**缺口四：社群點的 metadata 活不到畫面上（三段獨立斷點）。**
初版計畫宣稱「前端不用新增渲染分支」，**這是錯的**：

1. `parkingNote` 只在 `parkingSource === 'stop-data'` 時渲染（`:14633-14638`），`community` 來源不會顯示任何說明
2. `nearbyTdxParkings` 把候選壓成 `{ lat, lng, name }`（`:545`）——**`parkingSource`／`parkingNote` 在這裡就被丟掉**
3. `exportParkingLocal` 是白名單輸出（`crawler/worker.js:1336-1344`），只放行 name/lat/lng/address/phone/各類車位數/notes——`source`／`kind`／`reports`／`lastConfirmedAt` **根本進不了 `parking-data.js`**

**座標本身可以被採用，但要讓社群點「看起來像社群點」，這三處都得改。** 已納入排程（0d）。

### 1.3 收件人分析

現行 UI 三處宣稱這個回報是給同行者的（副標 `html:533`、情境列由 JS `:1386` 寫入、toast `:1433`）。**這個定位是錯的。**

回報機制在「即時協調」這件事上是在跟 LINE 競爭，而且必輸：同一趟行程的人彼此認識、同時在場，
「停車場滿了，往前開兩百公尺」用訊息三秒講完；要對方開 app、找到行程、找到那一站、讀一則回報，成本高出一個數量級。
**為這種情境設計，等於做一個比 LINE 難用的 LINE。**

> **關於審查意見的處理**：Codex 曾以「分兩台車／先到者場勘／成員分批抵達／長輩需知道入口與付款方式」
> 主張同行者可見仍有價值。經評估**不採納**——前三項都是打電話嚴格更好的情境；
> 第四項「長輩需知道入口與付款方式」根本不是即時協調，而是**關於這個地點的資訊**，
> 正好該由累積後的資料層提供。該反駁的最佳例證反而支持本節結論。

回報服務的是三種對象，沒有一種是同行者：

| 回報 | 真正的收件人 | 發揮價值的時機 |
|---|---|---|
| 找到停車場（＋位置） | 未來到訪的人 | 累積後促進成停車點 |
| 地圖位置不正確／不存在 | 系統／資料維護 | 修正或刪除錯誤資料 |
| 停車場已滿 | 未來規劃行程的人 | 累積成「這裡常滿」的統計 |

**推論：即時狀態的價值不在即時，在統計。**
既然沒有人正在即時觀看，就不需要為「新鮮度」設計任何東西。

### 1.4 被推翻的假設

- **A：「回報是給同行者看的」→ 錯。** 見 1.3。UI 文案必須跟著改。
- **B：「把回報顯示出來是投入最小、落差最大的一步」→ 錯。** 收件人不是同行者，顯示出來不會產生價值。第一優先是**補上座標**。
- **C：「階段 0 本身就有價值，不依賴聚合成立」→ 錯，且這是最大風險。** 緩解見 6.5。
- **D：「聚合的難點是 GPS 精度」→ 錯。** 難點是根本沒收座標。
- **E：「前端不用改」→ 錯。** 見 1.2 缺口四，三處都要改。
- **F：「地理圍籬能擋住假座標」→ 錯。** `destLat/destLng` 若由前端提供，攻擊者把目的地改成與假位置相同即可通過。見 4.4。

## 二、整體架構

```
前端  ──POST /api/parking-report──→  後端驗證（destId 反查、accuracy、rate limit）
                                          │ Admin SDK
                                          ▼
                                   parking_reports（原始，Admin-only，90 天保留）
                                          │ crawler 聚合
                                          ▼
台東縣府 XLSX ──crawl:parking──→  parking_lots ──export:local──→ app/parking-data.js
                                                                        │
                                                    resolveParkingCoord 第 2 層採用
```

**兩個 Firestore 集合都是 `allow read, write: if false`**——前端本來就只讀靜態檔，
沒有理由再開 Firestore 查詢面。「我的回報」走 `GET /api/parking-reports/mine`。

這比照既有的 `generation_runs` 模式（`firestore.rules:612` 為 `allow write: if false`，只由後端 Admin SDK 寫入）——
**不是另建架構，是在既有信任邊界上擴充。**

## 三、階段 0：讓回報變成可用的資料

### 3.1 回報加上座標 —— 第一優先

「找到停車場」不再只是選項，而是**帶位置的動作**：選了它就接既有的位置標記流程
（`openParkingRecordSheet`），讓使用者確認或拖曳圖釘。

**這是整個功能唯一有實質產出的動作。** 沒有座標，後面全部不成立。

### 3.2 選項重整：依收件人拆開

**第一層——這一站有沒有地方停？**（資料層，累積成統計）
- ✅ 有，我停好了 → **接位置標記**（3.1）
- ⚠️ 有停車場但停不進去 → 細分「已滿」／「今天沒開」
- ❌ 附近真的沒有停車場

**第二層——資料有錯**（系統層，獨立送出）
- 位置標錯
- 這個停車場不存在

預設值改成未選取（目前預設「找到停車場」，誤按送出就會關掉警示）。

### 3.3 UI 文案改寫

| 位置 | 現行 | 改為 |
|---|---|---|
| 副標 `html:533` | 協助同行者知道這一站的停車狀況 | 回報停車狀況，幫助之後來的人 |
| 情境列 JS `:1386` | 回報會同步給這份行程的成員 | 回報會用來改善這個地點的停車資訊 |
| Toast `:1433` | 已同步給同行者 | 已收到回報，謝謝 |

### 3.4 `type → parkingFound` 的語意修正

不再用布林壓縮，至少三態：`stage.parkingState = 'available' | 'blocked' | 'none'`。
「已滿」顯示「這一站的停車場曾被回報已滿」，不是「找不到鄰近停車場」。

### 3.5 前端三處修改（缺口四）

1. `parkingNote` 的渲染條件從 `=== 'stop-data'` 放寬為「有 `parkingNote` 就顯示」
2. `nearbyTdxParkings` 保留 `parkingSource`／`parkingNote`／`kind`，不要壓成三欄
3. `exportParkingLocal` 白名單加入 `source`／`kind`／`reports`／`lastConfirmedAt`

### 3.6 第一層短路的處理（缺口四延伸）

`getEmbeddedParkingHint` 會在社群點之前短路。若某景點的描述提到「停車場」但實際上沒有，
社群點永遠用不到。**建議：社群點的信心等級若為「正式」，應優先於 embedded hint。**
這是設計決策，動工前要定案。

### 3.7 （可選）同行者可見

排在所有資料層工作之後，做不做都不影響本計畫成立。理由見 1.3。

## 四、階段 1：後端寫入邊界

### 4.1 為何不讓前端直寫

前端直寫（原方案 A）把敏感原始資料的寫入面直接暴露，且無法可靠做限流、重放防護與伺服器端目的地核對。
Firestore 規則能表達的驗證有限（尤其地理圍籬），而 **Admin SDK 會繞過 Rules**——
端點若驗證漏掉欄位，Rules 不會補救。因此驗證責任全部落在後端，必須寫嚴。

### 4.2 資料格式

```js
// parking_reports（Admin-only，90 天保留）
{
  lat, lng,          // 4 位小數（≈11m）
  accuracy,          // > 50 拒收
  adjusted,          // 使用者是否拖曳修正過
  kind,              // 'lot' | 'roadside' | 'temp'（temp 不促進）
  state,             // 'available' | 'blocked' | 'none'
  destId,            // ★ 不是座標。由後端反查，見 4.4
  uid,               // ★ 取自 token，不接受前端提供
  at,                // ★ Timestamp.now()，不接受前端提供
  note               // 極短限長；★ 永遠不進 parking-data.js
}
```

### 4.3 Firestore 規則（需使用者部署）

```
match /parking_reports/{id} { allow read, write: if false; }
match /parking_lots/{id}    { allow read, write: if false; }
```

前端不碰這兩個集合。讀走靜態檔，寫走後端端點，查自己的走 `GET /api/parking-reports/mine`。

### 4.4 地理圍籬：關鍵修正

**不可接受前端傳來的 `destLat`／`destLng`。**
攻擊者只要把目的地座標改成與假位置相同，800m 檢查必定通過——圍籬形同虛設。

改為前端只傳 `destId`，後端從可信景點資料或**使用者有權限的行程 stop** 反查座標後計算距離。

即使如此，瀏覽器的 `lat/lng/accuracy` 仍可偽造。
**地理圍籬是資料品質檢查，不是反作弊證明**——反作弊靠 6.6 的聚合門檻。

> 註：Firestore Rules 內建 `LatLng.distance()`，理論上規則層也能算距離。
> 但因 `destId` 反查必須在後端做，這條路仍不可行。**動工前請確認該 API 在你的 Rules 版本可用**（本計畫未驗證）。

### 4.5 限流（不需要 Redis）

- IP：每小時 30 次，放在 token 驗證**之前**
- UID：每天 10 次，放在 `requireFirebaseUser` **之後**
- **完整性限制**：同一 UID、同一 destId、30 天內最多一票——比 HTTP 限流更重要，因為伺服器重啟不該讓同一人重新灌票

⚠ **body parser 順序問題**：`server.js:76` 的 `express.json({ limit: '5mb' })` 在所有 `rateLimit` 之前，
攻擊者可先送大型 JSON 消耗解析資源。停車回報路徑應在 nginx 限到幾 KB，或改用小型 route parser。

### 4.6 刪除權（矛盾已解消）

初版把「不可 update/delete」與個資刪除權當成兩難。**其實不衝突**：
`allow update, delete: if false` 只約束**客戶端**，後端 Admin SDK 仍可刪。

做法：提供本人專用的後端刪除端點——
1. 驗證 token 與文件 `uid`
2. 立即將該回報排除於聚合
3. **真的刪除**含 uid／座標／時間／note 的原始文件
4. 只留最小化處理紀錄（隨機請求編號、時間、結果），**不保留原座標與 uid**
5. 標記該 destId 需重新聚合；剩餘獨立回報者不足門檻則下次匯出撤下

> 只加 `deleted: true` 卻保留原始位置，不等於刪除。以個資法第 3、11 條為設計底線。

原始回報設 **90 天自動保存期限**。聚合結果只有在已移除 uid、備註、精確時間、來源 ID 後才適合長期保留。

## 五、階段 2：群聚與促進

### 5.1 何時做

**不要現在做。** 門檻與半徑在沒有真實資料前無法決定。與 POI 精度那次一致：先量再決定。

### 5.2 群聚半徑：25–30 公尺（**待驗證參數，非定案**）

初始假設來自 `TRAVEL_STORY_EXPORT_PLAN.md` 附錄的實測：4 位小數網格 ≈11m、
去重後兩個真正不同的地點最近相隔 39m。

**但這份實測是景點／照片配對的資料，不必然適用停車場**：GPS 誤差 20–50m、
停車場入口與場域本身有面積。**這個數字要用真實回報分布驗證後才定案。**

### 5.3 精度守門

| 條件 | 處理 |
|---|---|
| `adjusted === true` | 最高信心 |
| `accuracy ≤ 30` | 採用 |
| `30 < accuracy ≤ 50` | 採用但降權 |
| `accuracy > 50` | **拒收** |

### 5.4 信心等級

| 條件 | 呈現 | 進 `parking-data.js` |
|---|---|---|
| 1 筆 | 「1 位旅伴曾停在這」 | 否（僅回報者本人可見，見 6.5） |
| ≥2 位不同 uid | 「多位旅伴回報」 | 否 |
| 符合 6.6 全部條件 | 正式停車點 | **是** |

### 5.5 停車場屬性統計

「已滿」「今天沒開」不促進成新點，而是累積成既有停車場的屬性
（`fullReports`／`closedReports`／`lastFullAt`），供生成行程時提前提示替代方案。
**這是 1.3 那個推論的具體落地。**

### 5.6 落地格式

```json
{ "name": "多良車站旁（旅伴回報）", "lat": 22.5075, "lng": 120.9589,
  "source": "community", "kind": "roadside", "reports": 3, "lastConfirmedAt": "2026-08-01" }
```

新增 crawler 模式 `--promote-parking`。⚠ 產生 `parking-data.js` 時**必須用安全的 JSON 序列化，不可字串拼接**——
否則是注入管道（`note` 一律不進此檔）。

## 六、風險與防護

### 6.1 違規停車被正當化 —— 最需要防

三個人臨停紅線，系統就開始「推薦」違停地點。**這是會出事的，不只是資料品質問題。**
防護：`kind` 必填，**只有 `lot`／`roadside` 能被促進**，`temp` 只留給回報者自己看且設短 TTL。

### 6.2 私人／店家停車場

同 6.1 的分類問題，必要時加一題「是否對外開放」。

### 6.3 隱私

停車位置＝使用者當時的所在位置。
- 原始回報**前端不可讀**（4.3），只由後端寫入、90 天後刪除
- 公開資料只有群聚後的中心點，不帶 uid、不帶個別時間
- 地理圍籬（離目的地 800m 內）由**後端**執行
- 隱私日誌：request body、座標、token **不得寫入 Express／nginx 日誌**
- 最小蒐集：只存 `destId`，不同時保存可重建的目的地座標

### 6.4 時效與腐爛

`lastConfirmedAt` 超過 12 個月未再確認 → 降級並從 `parking-data.js` 移除。

### 6.5 冷啟動 —— 最大風險

台東一年可能只有幾十趟行程，要等 3 位不同使用者在同一個停車場回報，可能永遠不會發生。

**必要緩解（與階段 1 同批做，不是後續優化）——個人層級立即生效**：

```
個人回報 → 個人層級立即可用（我的停車點）
        ↘ 符合 6.6 → 公開層級（社群停車點）
```

⚠ 這需要在 `resolveParkingCoord` 前多接一層個人資料來源——**這也是「前端要改」的一部分**，
不是純資料工作。已納入排程。

### 6.6 Sybil 攻擊 —— 灌票防禦

真正的風險不是單帳號高頻，是**多帳號灌票**。
**聚合門檻不能算文件筆數，必須算「符合資格的不同 UID 數」**，並同時滿足：

- 至少 3 個**信箱已驗證**的不同帳號
- 分布在至少 **2 個不同日期**
- 每個 UID 對同一 destId 只算一票
- 座標形成 **30–50m 內的合理群集**（不是只要落在 800m 圍籬內）
- `kind` 大致一致
- **新帳號先收下但不列入門檻計算**（帳號 first-seen 未滿數日者不計）
- **可降級可撤下**：因否定回報、刪除或過期而下架，不可只升不降

其他必處理：重放攻擊（idempotency key）、`NaN`／`Infinity` 拒收、座標範圍驗證、欄位白名單。

> 接受一個現實：**純網頁無法證明使用者真的在現場。**
> 因此設計原則是「寧可慢一點收錄，也不要讓少量可疑帳號污染全體資料」。
