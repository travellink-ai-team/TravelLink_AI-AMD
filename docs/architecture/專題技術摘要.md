# TravelLink AI — 專題技術摘要

> AI 微旅行規劃系統（網頁端）｜舊名 WanderAI，2026-07-26 更名
> 正式站：`https://travel-link-ai.duckdns.org/`
> 本文依 repo 快照撰寫：commit `a6f61f7`（2026-09-03），統計時間 2026-09-17。未追蹤的 `app/travel-memory-demo.*` 不列入。
> 本專題為雙端專案：本 repo 是**網頁端＋後端代理＋資料管線**；Android App 由組員另行開發，兩端共用同一個 Firestore（本文提到「App 端」指的是它）。

## 1. 系統要解決的問題與目標使用者

### 1.1 問題

用 LLM 直接「幫我排一日遊」會碰到幾個很實際的問題，本系統就是針對這些問題設計的：

| 問題 | 具體表現 | 系統的對應設計 |
|---|---|---|
| **景點幻覺** | LLM 會編出不存在的景點、給錯座標，或把新竹的「南寮漁港」配到綠島 | 已驗證景點白名單＋逐站 Places 嚴格比對（§6.1） |
| **行程不可執行** | 路線南北來回、總時長超出、排到公休日的店 | 客戶端路線最佳化、時長填補／壓縮、依日期判斷營業時間（§4.2） |
| **成本失控** | 每次生成都打 Google Places，每站一次，費用隨使用量線性成長 | 本地優先的靜態資料快取、可歸因的成本統計（§6.1、§6.3） |
| **偏鄉資訊缺口** | 台東停車場、門票、離島船班這類資料在 Google 上又少又不準 | 爬政府 OpenData、群眾回報停車點（§4.6、§6.5） |
| **多人出遊協調** | 每個人偏好不同、同時編輯會互相覆蓋 | 偏好彙整＋三方合併＋重新生成鎖（§6.4） |

### 1.2 目標使用者

- **主要**：到**台東本島與離島（綠島、蘭嶼）**的自由行旅客，時間從 2 小時到兩天一夜，交通方式是自駕、機車或計程車。從資料覆蓋就看得出這個定位：`app/poi-data.js` 共 288 個景點，其中台東 198、綠島 47、蘭嶼 24。
- **次要**：多人同行的團體（上限 10 人，見 `app/collab.js` 的 `MAX_MEMBERS`），以及只拿到分享連結、沒有登入的訪客（唯讀）。

### 2.2 分層說明

| 層 | 實作 | 重點 |
|---|---|---|
| 前端 | 原生 HTML/CSS/JS，**沒有框架、沒有建置步驟**，一律用 `<script src>`（不用 ES module），所以 `file://` 也能直接開 | 兩個主頁面的邏輯分別在 `app/ai-travel-explore-final.js`（7,126 行）和 `app/ai-travel-planner-v8.js`（17,247 行） |
| 後端 | `server/server.js` 單一 Express 程序，**只監聽 127.0.0.1**，對外一律經過 nginx | 有四個職責：藏金鑰、驗證身分與限流、做 Rules 表達不了的驗證、執行重運算（渲染影片） |
| 資料庫 | Cloud Firestore＋Cloud Storage | 權限寫在 `firestore.rules`（670 行）與 `storage.rules` |
| 資料管線 | `crawler/worker.js` 單檔 CLI | 把貴的外部 API 呼叫從「每次使用」移到「離線批次」 |
| 部署 | Windows 11 上跑 nginx＋Node 代理，`server/proxy-control.ps1` 管理程序，`DEPLOY.md` 記錄完整步驟 | nginx 的 `root` 指到 `app/`，這樣 `crawler/serviceAccount.json`、`.git/` 天生就不在網站根目錄底下 |

## 4. 主要功能模組與實作方式

### 4.1 旅行精靈（explore）

- **精靈步驟**：`renderWizard()`、`wizNext()`／`wizPrev()` 依序收集目的地、時長（小時制或多日）、人數、節奏、興趣、交通工具、起訖點、預算、想去的景點。
- **避免把時間排爆**：`getSafeSlotMinutes()`、`doesScheduleFitDuration()` 會限制預覽節點的時間間隔；`buildAutoDelayedPreviewTimes()` 實作「後面的站若早於或等於前一站就自動往後延，否則保留使用者手動輸入的時間」。
- **個人禁忌**：`app/avoid-tags.js` 提供標籤；`findDesiredSpotConflicts()` 會在使用者想去的景點和禁忌衝突時即時警告。
- **中斷恢復**：`finishWizard()` 先把空行程寫進 localStorage，並記下 `wai_pending_gen`，重新整理頁面後可以接著生成。

### 4.2 AI 行程生成管線（系統核心）

進入點是 `_doGeneration()`（`app/ai-travel-explore-final.js`），可以分成四個階段：

```
step0  準備上下文
       ├ fetchTripRainOutlook()     出發日 7 天內且目的地是台東 → 查 CWA 一週預報，下雨時注入「改排室內」規則
       ├ buildLocalPoiHintBlock()   本地已驗證景點清單（有就不打 Places）
       └ fetchGoogleMapsFoodList()  餐廳候選（本地優先）；景點與餐廳兩個 promise 並行送出
step1  LLM 生成
       └ requestGeminiMicroTravelPlan() → buildPrompt() → fetchGeminiStream()（SSE）
           onChunk 用 extractNamesFromStream() 即時顯示「已識別 N 個景點」
step2  後處理 optimizeGeneratedTripStops()
       ├ matchStopsToLivePlaces()        把 AI 選的名稱對回 Places 物件，直接取得權威座標
       ├ sanitizeStopCoordinates()       超出目的地半徑的座標清掉
       ├ enrichMissingCoordinates()      補上缺少的座標
       ├ isWithinCorridorKm()            起點→目的地→終點走廊過濾，先用 5 km，站數不夠再放寬到 10 km
       ├ verifyAndFilterStopsWithPlaces() 逐站真實性驗證（§6.1）
       ├ sortStopsByNearestRoute()       最近鄰居法＋2-opt
       ├ mergeNearbySubAttractions()     同一景區的子景點合併（800 m／同名 2 km）
       ├ enrichBigAttractionSubSpots()   大景區用 searchNearby 標出子景點
       ├ fillTripTimeBudget()            總時長不足 45 分鐘以上 → 再問 LLM 補站
       ├ reorderStopsAlongRoute() → applyTripPlanningRules() → assignTransportModes()
       ├ injectEndpointStops()           插入起訖站
       ├ fitGeneratedStopsToTimeLimit()  超時 → 平均縮短各站停留（水位填平法）
       ├ dayIndex 正規化                 多日行程：AI 常給「1,1,3,3」漏掉第 2 天 → 改用比例切分
       └ 公休標記                        extractDayHoursWindow() 依各站所屬日期判斷，只標記不刪站
step3  預算與收尾
       ├ attachStopAlternatives()        每站保留附近替代景點（Plan B）
       ├ enforceBudgetCap()              超過人均預算 → 把門票最貴的站換成 altNearby 裡的免費景點
       ├ persistMicroTripInBackground()  寫入 Firestore
       └ WAI_COST.completeRun()          成本統計收尾（§6.3）
```

**路線最佳化**用的不是單純距離，而是加權成本 `getWeightedLegCostMeters()`：

```
成本 = 直線距離 × 尖峰係數(getPeakTrafficMultiplier) × (1 + 0.06 × 壅塞關鍵字分數)
尖峰係數：07:00–09:30、17:00–19:30 → 1.35；前後各約 30–60 分鐘 → 1.15；其餘 → 1
```

先用 `buildNearestNeighborRoute()` 建出初始解，再用 `improveRouteWithTwoOpt()` 反覆反轉子段落，直到沒有改善為止；可以用 `lockFirstStop` 固定起點。

### 4.3 行程編輯與出遊模式（planner）

- **重新排程**：`buildReplanSchedule()`、`adjustOverlappingStops()`、`updateStopStayTime()`，對應 AGENTS.md 裡「手動改時間時，後續站只在衝突時才往後延」的規則。
- **營業時間**：`app/business-hours.js`（`window.WAI_HOURS`）是**全站唯一**的解析器，採 UMD 寫法，Node 測試也能直接載入。原則是「寧可回 unknown 也不要猜」：只認錨定在字串開頭的星期標籤（例如「星期一至星期五」這種區間），沒有標籤又剛好 7 段時才推測是從週一開始。
- **AI 管家對話**：`handleAiSendMessage()` 使用 `buildGeminiSystemPrompt()` 規定 JSON action schema（`add_stop` / `remove_stop` / `replace_stop` / `set_time` / `reorder`）。`applyAiItineraryActions()` 執行前會先用 `validateAiStopTemplate()` 驗證新增的景點真的在這個地區，並用 `findDuplicateStopByName()` 去重。
- **AI 重新規劃**：`replanWithAI()` 在共編行程中會先呼叫 `WAI_COLLAB.acquireRegenLock()`，拿不到鎖就拒絕執行，不冒著覆蓋別人的風險硬寫。
- **出遊中**：`completeCheckIn()` 逐站打卡，`renderRideMode()` 是乘車導覽，`syncUserLocationWatch()` 追蹤 GPS，`openFullTripNavigation()` 串接 Google Maps 導航。
- **地圖**：`calculateAndDisplayRoute()` 用 Directions 畫路線；`renderAllToiletMarkers()`／`searchPlacesForToilet()` 標出附近廁所；`fetchOsmBoundaryPath()` 從 Overpass 抓景區多邊形，`pickOsmBoundary()` 用質心距離和環半徑擋掉海灣、行政區這類錯誤匹配，結果快取在 localStorage。
- **天氣**：`refreshWeatherView()` 經代理讀 CWA，`getRainyTripDays()` 找出雨天，`swapStopWithAlternative()` 可以把戶外站換成室內替代景點。

### 4.4 費用估算

- **門票**：`getLocalPoiFeeMap()` 讀 `poi-data.js` 的 `fee/feeNote`，`getCuratedFee()` 讀人工維護的覆蓋層 `attraction-fee-config.js`，後者優先。
- **餐飲**：`getLocalFoodCostMap()` 讀 `restaurant-data.js` 的 `costPerPerson`，這個值是爬蟲從 Places 的 `priceRange` 取中位數，或用 `priceLevel` 對照表推估出來的。
- **交通**：`estimateTransportRough()` 加上 `getFerryRoundTrip()`（離島船票，設定在 `cost-config.js`）。
- **顯示**：`renderBudgetTracker()` 呈現人均預算明細。

### 4.5 多人共編、好友、通知

- `app/collab.js`（`window.WAI_COLLAB`）負責建立共編行程、邀請碼（base32 字母表去掉 0/O/1/I，用 `crypto.getRandomValues` 做拒絕取樣，避免取餘數造成的偏差）、角色（owner/editor/viewer）、偏好彙整。
- **團體偏好彙整** `aggregateGroupProfile()`：節奏用多數決（`majorityPace()`，平手時聽發起人的），預算取平均，興趣取聯集並依票數排序，禁忌取聯集並保留是誰提的。結果交給 `buildGroupPreferenceLines()` 放進 prompt。
- **即時同步**：`startCollabTripLiveSync()` 以 `onSnapshot` 監聽，`applyCollabRemoteUpdate()` 套用遠端變更，寫入時用 `mergeCollabStops()` 做三方合併（§6.4）。
- **好友**：`app/friends.js` 的文件 ID 是 `friendshipId()`，把兩人 email 的 hex key 排序後串接，所以同一對好友只會有一份文件。
- **通知**：`app/notifications.js` 寫在 `user_notifications/{emailHex}/items`。

### 4.6 停車

`resolveParkingCoord()` 依序嘗試多個來源，第一個找到的就用：

1. `pickMyParkingPoint()` — 使用者自己以前回報過的點，不必等聚合門檻（解決冷啟動問題）
2. `pickPromotedCommunityParking()` — 至少 3 位不同使用者回報過的社群點。它排在景點文字提示之前，因為後者只是在描述裡找「停車場」三個字，回傳的其實是景點本身的座標
3. `getEmbeddedParkingHint()` — 景點描述裡明確寫了附設停車場
4. `getLocalParkingList()` — 台東縣府路外停車場（`parking-data.js`，30 筆，只用於本島，離島跳過）
5. `fetchTdxParking()` → `listParkingFromPlaces()` — TDX／Google Places

選出候選後，`pickWalkableParking()` 會用 Directions 算步行時間，超過上限的候選不採用。回報流程是 `commitParkingReport()` → `sendParkingReportToBackend()` → `POST /api/parking-report`（§6.5）。

### 4.7 旅程回憶與回顧短片

- **拼貼圖**：`openMemoryStudio()`、`buildMemoryMasterCanvas()` 在 Canvas 上排版，`memoryAiEdit()` 讓 Gemini 調整版面，`memoryStartSave()` 把成品切片輸出。
- **回顧短片**：
  1. 前端 `startRecapVideo()` 整理站點、照片，並用 `resolveRecapRoutePoints()` 取得真實道路軌跡
  2. `POST /api/recap/render` → `server/recap-jobs.js` 的 `sanitizeTrip()` 只採用 stops 和路線點，**時間軸由伺服器用 `app/recap-manifest.js` 的 `buildRecapManifest()` 重算**
  3. `server/recap-renderer.js` 用 puppeteer 開啟 `app/recap-headless.html`，和前端預覽用的是**同一支** `recap-render.js`。優先在無頭瀏覽器裡用 MediaRecorder 即時錄 canvas，再用 ffmpeg 轉成 mp4（約 14 秒）；逐幀截圖（約 140 秒）只當 fallback
  4. 前端輪詢 job 狀態 → 下載 → 存 IndexedDB（`recapIdbPut()`）→ 盡力上傳 Storage `recap-videos/{uid}/{tripId}/`
- **防濫用**：全域序列化，同一時間只渲染一支；佇列上限 `MAX_QUEUE = 4`；影片長度上限 60 秒；最多 40 站。

| 模式 | 函式 | 說明 |

### 5.2 設計考量

1. **沿用單一 `micro_trips` 文件，而不是另開 `collab_trips`**：個人行程和共編行程只差 `collab: true` 加上成員欄位，「個人行程轉成多人」就能在一筆 transaction 裡原地完成（`/api/collab/join-requests/resolve`），也不用做兩套查詢。代價是 Rules 的 `update` 分支變得很長。
2. **`stops` 用陣列內嵌，不拆成子集合**：一份行程通常只有 5–15 站，整份一起讀寫成本最低，也方便 App 端直接讀。缺點是同時寫入會整個陣列衝突，所以才需要 §6.4 的應用層三方合併。
3. **兩種身分 key 並存**：`memberKey()`（非英數字元一律換底線，舊 schema）和 `identityKey()`（UTF-8 轉 hex，無碰撞，用在文件路徑）。Rules 裡特別註明 `toHexString()` 輸出大寫，要再 `lower()` 才對得上 Web 端產生的 key。舊 key 的碰撞風險記錄在 §8。
4. **成本欄位的反向保護**：`costFieldNames()` 列出 11 個保留欄位，`touchesCostFields()`／`createsCostFields()` 禁止它們出現在 `micro_trips`。就算後端算得再準，只要用戶端能在行程文件上寫一個假的 `costUsd`，畫面就可能顯示假數字。
5. **把「必須反查其他文件才能驗證」的寫入移到後端**：例如「回報位置必須在該行程某一站的 800 m 內」，這種條件 Rules 表達不了，所以該集合直接全關，只能由 Admin SDK 寫入。
6. **為 Android 端相容而放寬的地方**：`inviteCode != ''` 的行程任何登入者都可以讀（App 用 `whereEqualTo inviteCode` 查詢）；舊版 6 位 PIN 的 `joinPinValid()` 是過渡期規則。這是跨端相容的取捨，列為已知限制。

## 6. 技術難點與設計取捨

### 6.1 LLM 幻覺與 Places 成本的雙重約束：「本地已驗證白名單＋嚴格比對＋短路」

**問題**
Gemini 生成的景點名稱可能不存在，座標也不可信。如果每站都呼叫 Places `searchText` 來驗證，一次生成就要 8–15 次付費呼叫，再加上 `fillTripTimeBudget` 補站又是一輪。另外，Places 的 top-1 結果常被通用後綴誤導，例如搜「XX 漁港」「XX 部落」會跑到別的縣市的同名地點。

**最後的做法**
1. **離線把驗證做完**：`crawler/worker.js verifyPlaces()` 事先把 OpenData 景點逐筆比對 Places，通過的標記 `placeVerified: true` 並匯出到 `poi-data.js`（目前 288 筆中有 227 筆已驗證）。
2. **在 prompt 限制選擇範圍**：`buildLocalPoiHintBlock()` 把本地清單放進 prompt，規則要求「只能從清單挑」。唯一例外是使用者指定的景點（`desiredNote`），而且禁忌衝突優先於指定。
3. **執行期短路**：`verifyAndFilterStopsWithPlaces()` 先建一張 `_localVerifiedByName` 表（本地景點＋快取餐廳），名稱命中就直接採用本地座標與營業時間，**不打 Places**；`coordinateSource === 'google_places_matched'` 的站也同樣短路。
4. **沒命中才打 Places，而且要嚴格比對**：`maxResultCount: 5` 取多筆候選，逐筆檢查 `placeNameMatchesQuery()`（去標點、「臺」轉「台」、剝掉 `GENERIC_PLACE_SUFFIXES` 後比對核心名稱）**並且**要在目的地半徑內。都不符合時**保留該站、標成 `placeVerified: false`**，不會隨便套一個錯的座標。
5. **離島特例**：`WAI_FERRY_CONFIG.islandHarbor` 直接提供港口座標，避免「南寮漁港」被 geocode 到新竹。
6. **防止誤刪**：驗證後如果真正的景點少於 2 個就退回原始清單（`mainStops.length >= 2 ? … : stops`），並排除起訖交通樞紐，避免「只剩起點和終點也算通過」。

**為什麼選這個做法**
- 完全相信 LLM：座標錯誤會直接造成導航錯誤，對使用者傷害最大。
- 每站都即時驗證：延遲和成本都隨站數線性成長，而台東景點變動很慢，每次重新驗證沒有資訊增益。
- 向量資料庫／RAG：單一目的地的候選景點只有幾十到兩百筆，直接放進 prompt 就夠用，另外建檢索服務沒有必要，也和專案「無建置、純靜態」的限制衝突。
- 靜態 JS 檔而不是每次查 Firestore：CDN 或 nginx 可以快取，也少一次網路往返；更新頻率低，由爬蟲批次產生即可。

### 6.2 生成延遲與品質的取捨：關閉 thinking，把品質防線移到客戶端演算法

**問題**
`gemini-3-flash-preview` 預設會開 thinking。專案在正式站實測過（紀錄在 `buildGenConfig()` 的註解）：同一個 prompt，預設模式 1,224 thinking tokens／9.6 秒，`thinkingBudget: 0` 是 0 tokens／3.5 秒；主生成的大 prompt 用 `low` 時 thinking 仍會超過數千 tokens，首個 token 要等 30 秒以上，還會把 `maxOutputTokens` 吃光，導致 JSON 被截斷。

**最後的做法**
- 所有需要 JSON 的呼叫一律 `thinkingBudget: 0`。
- **路線品質交給確定性演算法**：`sortStopsByNearestRoute()`（最近鄰居法＋2-opt，加權尖峰係數）、`reorderStopsAlongRoute()`，合併與補站之後會再重排一次。
- **時長交給兩個互補的函式**：
  - 太短：`fillTripTimeBudget()` 原本最多 3 輪，每輪都是 1 次 Gemini 加 2 波 Places 串行，這是生成尾端最大的延遲來源。**改成 1 輪、每次多要 3 個備用候選**，用候選數量換取命中率。
  - 太長：`fitGeneratedStopsToTimeLimit()` 用水位填平法平均分攤縮短量，每站最多縮 35%，餐廳不縮；如果還是超時，才從停留最久的站再扣（每站至少保留 5 分鐘）。
- **串流**：`fetchGeminiStream()` 的逾時分兩段：連線階段 90 秒（離島或多日行程的大 prompt，首個 token 常超過 60 秒），開始收資料後改成「90 秒沒有新資料才中止」，避免誤殺正常的長回應。
- **公休只標記、不刪除**：`optimizeGeneratedTripStops()` 最後一步只設定 `scheduleWarning = 'closed_today'`。註解記錄了實測結果：到這一步才刪站，會推翻前面已經完成的缺日防護、時間寫入和時長壓縮，造成「某一天整天空白」和「時間出現空檔」。

**為什麼選這個做法**
「路線不要來回跑」「總時長 ≤ N 分鐘」這類約束，確定性演算法可以**保證**做到，也能測試；LLM 推理只能「傾向」做到。3.5 秒和 30 秒以上的等待體驗差距很大，所以把 LLM 定位成「從候選清單挑景點＋寫描述」，其他交給程式處理。

### 6.3 在不破壞串流的前提下，做出使用者無法竄改的 API 成本統計

**問題**
想在每筆行程上顯示「這次生成花了多少」，但有三個限制：
1. 一次生成會觸發很多 Gemini 和 Places 呼叫，分散在各個函式裡。
2. 用量資訊（`usageMetadata`）在 SSE 串流的**最後一個事件**裡，但代理必須逐塊轉發，否則前端「景點名稱逐一浮現」的效果會消失。
3. 計算出來的金額必須是使用者改不了的。

**最後的做法**
- **runId 歸因**：`POST /api/generation-runs/start` 核發一個 `crypto.randomBytes(24)` 產生的 runId，綁定呼叫者的 uid。之後每次代理請求都帶 `X-Run-Id`，伺服器用 `getOwnedRun()` 核對擁有者。
- **旁路解析，不阻斷串流**：`server/usage-tap.js createUsageTap()` 的設計是「餵什麼看什麼」。`server.js` 裡 `res.write(buf)` 的時機完全不變，同一塊 bytes 另外丟進 `tap.feed(buf)`；SSE 以最後一個帶 usage 的事件為準；非串流回應最多緩衝 8 MB；解析失敗一律靜默，不影響回應。
- **記憶體累加，一次落地**：`server/generation-runs.js` 用 Map 累加，收尾時才寫 Firestore，避免同一份文件被寫很多次。記憶體有上限：`MAX_RUNS = 500`、每個 uid 最多 20 個、閒置 30 分鐘強制收尾；淘汰會**同步**從 Map 移除，以免一連串 create 在 flush 回來前就衝破上限；還在處理中的請求用 `retain()`／`release()` 保護。
- **誠實的不完整狀態**：沒收到 finish、上游出錯、讀不到 usage 的 run 一律記成 `billingStatus: incomplete`，畫面顯示「統計未完成」而**不是 0 元**。沒有費率的模型（圖片模型）記進 `unpriced[]`，不算成 0。
- **三層信任邊界**（`server/pricing.js`）：`authoritativeUsage`（後端觀察）／`costUsd`（後端依 `PRICING_VERSION` 估算）／`clientReportedUsage`（Maps JS SDK 的次數，後端看不到，只能由前端回報，UI 會另外標示）。費率表**只存在伺服器端**。
- **前端競態修正**：`app/cost-tracking.js` 原本用全域變數保存 runId，使用者連續切換行程時會把用量記到錯的 run。後來改成每個 run 是一個物件，所有非同步操作都綁定傳進來的那個物件，不在執行時回頭讀全域狀態，並用 promise 序列鎖讓 `ensureRun` 的「判斷＋建立」互斥。

**為什麼選這個做法**
- 用 Cloud Billing：只能看整個專案的總額，無法歸因到單筆行程。
- 前端自己計算：使用者改一下 JS 就能改金額，失去「權威」的意義。
- 每次呼叫都寫 Firestore：寫入放大，而且那些寫入本身也要錢。
- 取捨：伺服器中途重啟會遺失還沒落地的累加。但這個情況會被 `incomplete` 如實揭露，而不是悄悄少算。

### 6.4 網頁與 App 雙端共編的一致性：交易內三方合併＋重新生成鎖＋後端核發加入憑證

**問題**
- `stops` 是一個陣列。兩位成員同時編輯時，Firestore 的 `set(merge)` 會用後寫入的整個陣列覆蓋前一個人的修改。
- App 端讀的欄位格式不同（頂層 `transportMode`、帶簽章的 `transitMins`），網頁端寫入時必須兩邊都照顧到。
- 邀請碼如果在前端驗證，等於把「任何人都能把自己加入任何行程」的能力交給用戶端。

**最後的做法**
- **三方合併** `mergeCollabStops(remote, base, local)`（`app/ai-travel-planner-v8.js`）：
  - `base` 是本頁上次看到的版本，`local` 是這次的修改，`remote` 是**交易內**讀到的最新版本。
  - 每一站用 `getStableCollabStopId()` 取得穩定 ID，只把「local 相對 base 真的改了」的**欄位**套到 remote 上。所以不同站的修改，甚至同一站的不同欄位，都可以同時保留。
  - base 裡有、local 裡沒有的站視為刪除；站序只有在 local 真的重排時才採用 local 的順序。
- **在交易裡執行**：`persistCurrentTripStops()` 用 `runTransaction` 包住「讀 remote → 合併 → 寫入」。交通工具欄位也用同樣的三方判斷；`transitMins` 的簽章**依合併後的站序重算**，否則 App 會判定資料過期並整份丟棄。提交後立刻用實際寫入的結果更新 `collabBaseStops`，避免下一次延遲存檔把剛合併進來的遠端欄位誤判成本地修改而蓋回去。
- **寫入佇列**：`persistTripWriteActive`／`persistTripWriteQueued` 保證同一頁面同時只有一個交易在執行。
- **結構欄位分權**：內容存檔會明確排除 `members`、`ownerEmail`、`inviteCode` 等欄位，這些只由 `collab.js` 或後端處理，並搭配 Rules 的 editor 白名單。
- **整份重新生成**用 `acquireRegenLock()` 寫入 `regenLock{by, byName, at}`，Rules 的 `validRegenLockChange()` 只允許動這一個欄位。
- **加入流程**：`POST /api/collab/invites/verify` 由後端驗證邀請碼，然後寫入 `join_proofs/{uid}`（2 分鐘後失效）。Rules 的 `userHasJoinProof()` 檢查憑證存在、email 相符、未過期，而且 `memberEmails` 只能**增加自己一人**。分享連結的 token 用 `crypto.timingSafeEqual` 比對（`sameSecret()`），訪客只拿得到 `publicTripData()` 白名單欄位。

**為什麼選這個做法**
`collab.js` 開頭明確寫了產品範圍決策：「同看一份＋團體生成＋成員清單，**暫不做即時逐欄共編**」。在這個範圍下：
- 以「站」為單位的三方合併已經能處理實際的衝突情境（兩個人各改不同站）。
- CRDT 或 OT 需要改變資料模型，App 端也得一起重寫，雙端 10 週的排程承擔不起。
- 單純的「最後寫入者勝出」會無聲地遺失別人的修改，不能接受。

### 6.5 群眾回報停車點的信任邊界：伺服器反查目的地、地理圍籬、一人一票

**問題**
台東的停車資料很稀疏（TDX 對鄉村縣幾乎沒有覆蓋），所以讓使用者到現場回報。但回報資料是「使用者當時的實體位置」，同時帶來兩類風險：
- **偽造**：灌假資料、同一人重複投票。
- **隱私**：其他人可以列舉所有使用者的位置。

**最後的做法**（`server/server.js` 的 `POST /api/parking-report`，依據 `docs/停車回報群眾外包-實作計畫.md`，經過兩輪外部審查後修訂）
- **目的地座標一律由伺服器反查**：前端宣告站點座標後，後端在「這個使用者有權限的行程」的 `stops` 裡找距離 50 m 內的站，**採用資料庫裡的座標**。如果讓前端直接傳目的地座標，攻擊者只要把目的地設成和假位置一樣，800 m 圍籬就形同虛設。
- **地理圍籬** 800 m（`PARKING_GEOFENCE_METERS`）、定位精度 ≤ 50 m、經緯度範圍檢查放在所有類型分支**之外**（審查時發現可以用「經度 + 360」繞過 Haversine 圍籬）。
- **一人一票**：文件 ID 是 `destKey__uid`，`destKey` 用座標四捨五入到小數 4 位（約 11 m）產生，而**不是**用 `tripId + stopId`；同一人 30 天內再回報只是更新自己那一票。這樣「不同文件數」就直接等於「不同回報者數」，聚合時不需要另外去重。
- **型別嚴格**：`finiteNumber()` 只接受真正的 JSON number，因為 `Number(null) === 0` 會把「沒帶座標」變成 (0, 0)。
- **兩層限流**：IP 層放在驗證身分之前（未驗證的請求也要付出代價），UID 層放在驗證之後（換 IP 繞不過），並用套件的 `ipKeyGenerator` 處理 IPv6。
- **擋大型 payload**：先依 Content-Length 限制 8 KB，**再**掛一個路由專用的 8 KB JSON 解析器，因為 chunked 傳輸可以不帶 Content-Length。
- **真正的刪除權**：`DELETE /api/parking-report/:destKey` 會實際刪除文件（不是加 `deleted: true`），只留下不含 uid 和座標的稽核紀錄。
- **冷啟動**：聚合門檻是 3 位不同使用者，使用者少的時候幾乎不會達標，所以另外有 `GET /api/parking-reports/mine` 讓「自己的回報對自己立刻生效」。

**為什麼選這個做法**
Firestore Rules 表達不了「必須在該行程某一站的 800 m 內」這種需要反查其他文件的條件，也沒有可靠的限流。專案裡 `generation_runs` 已經有「集合對用戶端全關、只由 Admin SDK 寫入」的前例，所以沿用同一個模式。這樣信任邊界集中在一個端點，程式碼審查的範圍也比較清楚。

## 8. 已知限制與未來延伸方向

### 8.1 已知限制（有程式碼或註解佐證）

**架構與可維護性**
- **單一大檔**：`ai-travel-planner-v8.js` 有 17,247 行。為了維持「無建置、`file://` 可開」的限制而不用 ES module，結果是兩個頁面之間**邏輯重複而且已經分歧**。例如 `estimateTripMinutes()` 在 planner 版會把合併大景點的端點停留時間算進去，explore 版不會；`mergeNearbySubAttractions()`、`getLocalPoiList()`、`parseDurationMinutes()` 也各有一份。營業時間解析是目前唯一已經收斂成單一模組（`business-hours.js`）的部分。
- **測試不在正式模組上執行**：`test-e2e-logic.js` 靠字串抽取函式；`parking-report.test.js` 是**複製** `server.js` 的判斷式來測（檔頭註明「若那邊改了，這裡要同步」），兩邊可能不同步。沒有 CI，也沒有瀏覽器端的端對端自動化。

**演算法**
- **交通時間是啟發式估算**：`estimateLegMinutes()` 用直線距離 ÷ 40 km/h 估算，800 m 內固定算 10 分鐘，沒有考慮山路和海岸公路的繞行。尖峰係數也是固定表，不是即時路況。
- **路線最佳化沒有考慮時間窗**：最近鄰居法＋2-opt 只看加權距離，營業時間只在事後標記，不參與排序。本質上是 TSP with Time Windows 的簡化版。
- **LLM 仍有自由度的地方**：AI 管家的 system prompt 要求模型提供「廁所座標」（`buildGeminiSystemPrompt()`），這部分座標的可信度低於經過 Places 驗證的景點。

**資料覆蓋**
- 景點、餐廳、停車場、天氣都集中在台東（CWA 只查臺東縣；停車場只有縣府 30 筆）。
- 票價只覆蓋 288 個景點中的 27 個。
- `PLACES_RATES` 費率表刻意留空，圖片模型也沒有費率，所以成本統計目前**只有 Gemini 文字模型是完整的金額**。
- 社群停車點「從 `parking_reports` 聚合升級成 `parking_lots`」的批次程式還沒實作；前端讀取端（`pickPromotedCommunityParking()`）已經就緒。

**安全與權限**（程式裡標註的已知風險）
- `legacyMemberKey()` 把標點都換成底線，`a.b@x.com` 和 `a_b@x.com` 會變成同一個 key（`server.js` 註解「Codex 審查 #4」）。要根治必須連同 Rules 和 App 一起遷移到 `identityKey`。
- 加入申請的人數上限計算沒有把 owner 算進去，極端情況下申請會卡住（「審查 #3」）。
- 為了 App 相容，帶有 `inviteCode` 的行程任何登入者都能讀。

**部署與可用性**
- 單機部署：nginx、Node 代理、影片渲染都在同一台 Windows 主機上，沒有備援。
- `generation_runs` 的累加存在記憶體，重啟就遺失（會標成 incomplete）。
- 影片渲染全域序列化，`findChrome()` 寫死 Windows 路徑。
- 網站在 TANet 學術網路上，受校方網管政策影響（`DEPLOY.md` 有記載）。

### 8.2 未來延伸方向

| 方向 | 具體做法 | 對應現有基礎 |
|---|---|---|
| **帶時間窗的路線最佳化** | 把 `WAI_HOURS` 解析出的營業時段當成約束，實作 VRPTW 啟發式（插入法＋局部搜尋），或改用 Google Route Optimization API | `improveRouteWithTwoOpt()`、`business-hours.js` |
| **真實交通時間** | 在離線批次中用 Distance Matrix 建立景點兩兩之間的時間表並寫進 `poi-data.js`，執行期查表取代 `estimateLegMinutes()` | 爬蟲的 `export:local` 管線 |
| **模組化但保留無建置** | 把 explore 和 planner 重複的純函式抽成 UMD 模組（比照 `business-hours.js`），讓測試直接 `require` 正式程式碼 | `business-hours.js` 已經證明這個模式可行 |
| **量化評估 LLM 規劃品質** | 用 `travel_sessions` 的行為事件與 `feedback` 的 `aiScheduleAccurate/aiTransitAccurate/aiHoursAccurate` 建立指標，比較 thinking 開與關、不同 prompt 版本 | Rules 已經定義 App 端回饋 schema |

| **完整成本對帳** | 補齊 Places SKU 費率，依 `pricingVersion` 回頭重算歷史紀錄；再用 Cloud Billing 匯出資料和總量交叉核對 | `placesSkuKey()` 已經記錄 endpoint 與 FieldMask |

| **身分 key 遷移** | 共編 `members` 從 `memberKey` 遷移到 `identityKey`，並和 App 端、Rules 同步切換 | `identityKey()` 已經用在路徑類文件 |
